# 安全围栏设计说明

> 关联:COMPETITION.md §8 数据合规红线;评审维度"安全合规 10 分"。

本说明描述系统的**安全围栏**如何落地。围栏由四层构成:数据合规红线(§1)、只读三保险(§2)、四类合法性校验(§3,正是命题「设计安全围栏模块,验证表、指标、SQL 和结果合法性」的原话)、越界问题处理(§4),外加密钥与配置约束(§5)、LLM 故障兜底(§6)。§3 把命题原话逐字拆成四条,给出每条对应实现的**哪道门 + 代码行号**(行号均指 `text2sql_demo/text2sql.py`)。

## 1. 数据合规

- 数据集来源:比赛主办方提供的券商客户营销数据集(见 docs/数据说明.md)。
- 疑似个人字段:客户姓名 `name` 由数据源预脱敏;`sor_pty_id`(经纪客户号)经 `sensitive_columns` 注入后做**列级屏蔽**(样例不外发/SQL 引用拦截/结果掩码,见 §3b),演示输出客户明细聚合到看不出个体。
- 禁止联网抓取未授权数据、禁止引入外部真实个人信息。
- 全部结论可复现:评测命令见 README 与 docs/评测报告-基线.md。

## 2. 只读三保险(引擎既有,不动)

| 层级 | 措施 |
|---|---|
| 连接层 | `sqlite3.connect(f"file:{db}?mode=ro", uri=True)` 文件级只读 |
| 语句层 | `PRAGMA query_only=ON` SQLite 拒绝一切写操作 |
| 校验层 | 只放行单条 SELECT/WITH/EXPLAIN;剥离注释;多语句拒绝;`WITH` 解析主语句动词,拒绝 `WITH ... DELETE/UPDATE/INSERT/REPLACE/VALUES 非只读` |

## 3. 防幻觉围栏:命题「验证表、指标、SQL 和结果合法性」逐条对照

命题原话拆成四类合法性,**逐条**对应到实现的哪道门:

| 命题原话 | 对应哪道门(阶段 / 函数) | 判定要点 | 代码行号 |
|---|---|---|---|
| 验证**表**合法性 | ① 检索阶段逐字校验(`_retrieve`)② 计划检查 4.1(`_check_plan`) | 表名必须命中库元数据 `self.meta`(`get_table_meta` 直读 `sqlite_master`);未命中即丢弃 / 记 notes,不进入计划 | `:766`、`:776`、`:808` |
| 验证**指标**合法性 | 计划检查 4.4 / 4.6 + 口径断言 4.9(`_check_plan`) | 每个指标必须出现在计划文本;有指标必须有聚合;份额 vs 市值、交易额、盈亏等口径规则由注入侧 `caliber_assertions` 传入,违反即拒绝本次计划并重规划一次 | `:824`、`:832`、`:895-909` |
| 验证**SQL**合法性 | 安全校验阶段(`validate_sql`)+ 执行层双保险(`run_query`) | 剥注释(`:291`)→ 切语句(`:297`)→ 拒多语句(`:427`)→ 前缀白名单 SELECT/WITH/EXPLAIN(`:430`)→ `WITH` 主语句动词解析、拒写(`:352`、`:437`);执行再叠 `mode=ro`(`:443`)+ `PRAGMA query_only=ON`(`:445`) | `:420-438`、`:443-445` |
| 验证**结果**合法性 | 结果检查阶段(`_check_result`)+ 结果列缺失修复 | 空结果 / 仅 1 行 / 截断分别给出提示(`:1313`、`:1315`、`:1317`);计划声明的输出列必须出现在结果表头,缺失则复用修复机制重跑一次 | `:1313-1325`、`:1485-1497` |

- **SQL 编译器前端(AST)**: `sql_ast.py` 纯标准库词法 + 递归结构解析; `_ast_check` 在字符串校验之外做**语句结构/只读/真实表列**校验(错表、错列、`WITH` 后写语句均拦); CI 第 10 项 `sql-ast`(46 金标全可解析 + 负对照)。 另做**输出列投影**(`_project_result`): 计划声明列齐全时, 结果多出的列被确定性裁剪到声明列, 专门修掉 LLM 多输出列这类抖动。

以上四门之外的既有措施:

- 检索阶段:候选表/列与库元数据逐字校验,不存在的直接剔除并记录。
- 计划检查阶段(程序化):计划引用表必须存在;"表.列"引用必须真实;指标/维度/时间范围必须覆盖;有指标必须有聚合。
- SQL 校验阶段:见 §2。
- 评测判定器:表/列幻觉率结构化比对,基线恒为 0%(见评测报告)。
- 结果合法性检查(阶段 8):空结果、截断、单行分别给出提示,结论注明默认假设与数据局限。

## 3b. 受限字段列级屏蔽(隐私落地)

评审关注"数据脱敏处理到位、仅收集必要数据"。引擎提供**通用机制**, 具体受限列名由调用方经
`sensitive_columns` 注入(券商列名不硬编码进引擎;企业库经 `demo/enterprise_biz.json` 的
`sensitive_columns` 提供,评测侧由 `SENSITIVE_COLUMNS` 同源注入):

| 层 | 位置 | 行为 |
|---|---|---|
| 样例数据(出境前) | `build_schema(sensitive_columns=...)` | 该列样例行值以 `***` 占位,真实值不进入 prompt |
| SQL 语句(执行前) | `_validate` / `_repair_sql` 调 `_reject_sensitive` | 命中受限列(含别名/大小写/修复后 SQL)即拒绝并给出明确错误;字符串字面量不误伤 |
| 结果(展示前) | `_execute` 调 `_mask_sensitive_cells` | 结果表头命中受限列时以 `***` 掩码(双保险) |

- 机制测试:`python3 ci_check.py --only privacy`(样例 / SQL 直引 / SQL 别名 / 结果 四层 + 负对照)。
- 真实数据仍建议 `--sample-rows 0`, 从源头不让任何数据行进 prompt。

## 4. 越界问题处理

- 库外概念/闲聊/主观建议(如"今天天气怎么样?适合买基金吗?")→ 理解阶段 answerable=false,拒绝并给原因,不生成 SQL。
- 库中无引用表的码(300 证件/400 风险等级)→ 按不可答处理(口径红线,见评测口径定义 §3.4)。

## 5. 密钥与配置

- LLM 密钥在 `text2sql_demo/.env.local`(已被 .gitignore 排除),不打印、不入库、不进报告。
- 环境变量 `LLM_API_KEY` 亦可;支持 `LLM_BASE_URL`/`LLM_MODEL` 覆盖(私有化模型适配,不改代码)。
- UI 运行仅本地只读库;演示模式无需外部账号。

## 6. LLM 故障兜底

- 超时/连接/429/5xx:调用层指数退避重试 ≤3 次(R9);仍失败→阶段 FAIL 记录 + 友好错误卡片。
- JSON 输出空/截断:重试 1 次并提示精简;仍失败→阶段 FAIL,不崩溃。
- 全程 Trace 留痕,异常路径可审计。
