# 验证边界说明（我们证明了什么、没证明什么）

> 本文件**不重复评测数字**（那些在 [`评测报告-基线.md`](评测报告-基线.md) 与 [`benchmark/runs/`](../benchmark/runs/) 里）。
> 它只回答一个问题：**验收方自己能验到什么程度，以及我们没有验证的部分是什么。**
>
> 写作原则：能机器自证的不写成"应该没问题"；**没验证的直接写没验证**。区分三件事——
> ① 任何人都能一键复现的；② 我们在交付前真实跑过的；③ 我们**没有**跑过的。
>
> 更新于 2026-10-10（对应 commit `f704eb9`）。

## 1. 任何人都能一键自证的（零密钥、零数据、零联网）

```bash
git clone git@github.com:congxinjie/agentic-text2sql.git && cd agentic-text2sql
python3.11 ci_check.py            # 15 项工程自证
python3.11 demo/selfcheck.py      # 演示层无头自检(需先生成 marketing.db, 见下)
python3.11 bootstrap.py --no-serve --no-key   # 一键向导的"只检测不起服务"模式
```

| 入口 | 覆盖 | 实测（全新 clone） |
|---|---|---|
| `ci_check.py` | 15 项：语法 / 零第三方依赖 / 引擎解耦 / 判定器冻结 / 密钥泄露 / 合成库端到端（桩 LLM）/ SSE 契约 / 受限字段屏蔽 / 实体识别 / SQL 编译器前端 / 查询计划 / RAG 召回 / 任务分解 / 交互层 / 数据库适配层 | **15/15，0.63s**，不需要 `enterprise.db`、不需要密钥、不联网 |
| `demo/selfcheck.py` | 依赖 / 域词 / 口径同源 / judge 与 HEAD 一致 / 服务冒烟 / 首页要素 | **7/7 PASS**（需 `marketing.db`，向导会自动生成） |
| `bootstrap.py --no-serve --no-key` | 解释器探测 + 数据校验 + 上面两项 | 通过 |

> `ci_check.py` 的每一项都配了**负对照**（故意改坏 → 该项必须变红 → 复原，负对照不入库）：
> 改坏语法 → `syntax` 红；塞假密钥 → `secret` 红；改判定器一行 → `judge` 红；引擎塞券商域词 → `decouple` 红。
> 也就是说这 15 项不是"永远绿"的装饰。

**这部分是本文档里唯一"任何人都能独立复现"的结论。**

## 2. 交付前真实跑过的端到端路径

下表全部是**真实执行**的结果，不是推断。除注明外，均在 macOS + Python 3.11.16 +
`deepseek-v4-flash` 上跑。

### 2.1 一键向导（`bootstrap.py`）

| 路径 | 实测结果 |
|---|---|
| 全新 clone + **真实下载 88MB** | sha256 与仓库 `SHA256SUMS` 一致；8 张表 831447 行 / 7 索引校验通过 |
| 旧解释器起步 | 用 3.9.6 启动，自动找到并使用 `python3.11` |
| 找不到 3.10+ | 打印分平台安装命令（brew / winget / apt），`--yes` 下不擅自安装 |
| 密钥验证 | 真 key → `API 返回 200`；假 key → `密钥无效或已被吊销 (HTTP 401)` |
| 启动后真实冒烟 | 服务就绪 → 提问 → **12.7s 返回 2 列 / 6 行**，端到端打通 |
| 断点续传 5 场景 | 正常 206 追加 / 垃圾残留被 sha 拦截 / **越界残留 416 自愈** / 残留即完整文件 / 无残留整份下载 —— 落地内容 sha256 **全部逐字节正确** |
| 重复执行 | 幂等，环境齐备时约 30 秒直接进启动步骤 |
| `--port` 解析与退出码 | `--port 9100` / `--port=9200` 均正确；非法值退出码 2；`--help` 退出码 0 |
| 端口占用 | 8000 被占时自动选 8001 |
| Ctrl+C（SIGINT） | 日志出现"正在停止服务 → 已停止"，端口释放，无孤儿进程 |
| `kill -TERM`（SIGTERM） | 同上（此项是修复后复测，见 §4） |

### 2.2 接入自有数据库（`--adapter-module`）

| 路径 | 实测结果 |
|---|---|
| 陌生 SQLite 库零配置 | 电商库（`categories`/`products`/`orders`）不问业务背景直接提问 → **7.9s 正确**（家居 67.0 / 数码 685.67 / 服饰 299.0） |
| 注入业务口径 JSON（A/B） | `entities` 由 `[]` → 注入实体数组；`entities_covered` 由 `false` → `true`；`caliber_assertions` 由 `[]` → 命中展示 |
| 自写适配器接管数据访问 | 只用 `sqlite3` 写的 `RawSqliteAdapter`（不引用引擎任何实现）经 `--adapter-module` 注入 → `table_meta`/`schema_text`/`run_query` 全被调用，提问 **4.5s 返回 61（正确）** |
| DSN 形态 | `--db "mysql://..."` 不再被当文件路径校验，原样传给适配器 |
| 无参构造适配器 | 连 `--db` 都不给也能起服务并正确回答（连接从环境变量读） |
| 适配器内部抛异常 | 客户端拿到干净的 `RuntimeError: ...`，服务不崩（健康检查仍 200），堆栈只留服务端日志 |
| 错误路径 7 条 | 缺冒号 / 文件不存在 / 类不存在 / 模块属性非适配器 / 缺必需方法 / 两个参数都缺 —— 均给出可读中文提示 |
| 默认 SQLite 路径 | 无回归 |

> **注意**：上表验证的是**适配器机制**，用的是自己写的 SQLite 适配器。
> **我们没有连过真实的 MySQL / PostgreSQL / Hive。** 见 §3。

## 4. 交付前发现并修复的问题（缺陷史）

交付前做了一轮针对性补测（专门去打**只跑过主路径、没跑过分支**的地方），发现并修复：

| # | 问题 | 根因 | 处理 |
|---|---|---|---|
| 1 | 下载断点越界时，报错**把责任推给 Release**（"附件可能损坏或版本不符"） | `total` 用 `have + Content-Length` 计算，服务器只回 0 字节时算出与 `have` 相等的 `total`，完整性检查直接放行，最后才在 sha 处失败 | 改为以 `Content-Range` 总大小为准；HTTP 416 时丢弃残留自动整份重下（仅重试一次）。5 条场景复测全过 |
| 2 | `kill -TERM` 后演示服务变**孤儿进程**、占住端口 | 默认 SIGTERM 立即结束进程，连 `finally` 都不执行 | 新增 `install_termination_handler()`，把 SIGTERM/SIGBREAK 转成 `KeyboardInterrupt`，复用既有清理逻辑。复测端口正常释放 |
| 3 | 非 SQLite 库的**失败自修复静默失效** | 引擎修复判定是 `except (sqlite3.Error, ValueError)`（`text2sql.py` 第 1633 行），驱动自身的 `OperationalError` 不在其中 | **已写进文档并给出包装写法**（`run_query` 失败抛 `ValueError`）；**引擎那一行未改** —— 放宽判定属于改引擎行为，见 §5 |

**实测对照（问题 3）** —— 同一个适配器，只改抛出的异常类型：

| 首次执行抛 | 轨迹 | 结果 |
|---|---|---|
| `RuntimeError` | 无修复记录，直接报错 | ❌ 自修复未触发 |
| `ValueError` | `执行 WARN: SQL 修复后重试` → `执行 OK` | ✅ 生效，最终出表 |

**另一件值得记录的事**：补测过程中我们一度报告"Ctrl+C 没有清理子进程"，
复核后确认是**测试脚本自身的假象**（bash 会给后台进程把 SIGINT 设为忽略，`kill -INT` 等于没发），
用显式恢复默认信号处理的包装重测后，Ctrl+C 路径完全正常。**该结论已撤回，不是产品缺陷。**
把它写在这里是因为：把测试假象误报成缺陷，和漏报真缺陷一样有害。

## 5. 已知限制（是能力边界，不是待修 bug）

1. **失败自修复的触发条件**：引擎只对 `sqlite3.Error` 与 `ValueError` 触发"自动改一遍再试"。
   写自有适配器时需在 `run_query` 里把驱动异常包成 `ValueError`，否则该特性不生效（详见
   [`数据库适配方案.md`](数据库适配方案.md) 第 3 节）。
2. **评测数字的适用范围**：46/46、100%、P50/P90 等**只对本项目的 `enterprise.db` + 注入的券商口径有效**。
   换任意库后口径断言、few-shot、实体词表均为空，准确率无任何保证，需按
   [`评测口径定义.md`](评测口径定义.md) 自建评测集重新评估。
3. **`marketing.db` 不入库**（铁律：`*.db` 一律不入 git），全新 clone 必须先跑
   `python3 customer_marketing_db/create_db.py`，否则演示小库相关命令会报"数据库不存在"。
   一键向导会自动补这一步。
4. **`enterprise.db` 通过 GitHub Release 分发**（88MB，不入 git），首次需下载并校验。
5. **不内置任何数据库驱动**（守"引擎零第三方依赖"铁律），非 SQLite 库由使用方自备驱动 + 自写适配器。
6. **数据合规由使用方兜底**：`sensitive_columns` 不注入就没有列级屏蔽；样例数据默认
   `--sample-rows 0`（不外发 LLM），但查询结果本身仍会出现在页面与 CSV 导出里。
