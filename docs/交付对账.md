## 5. 本轮增补记录(2026-10-06): 数据集与主库走 Release, 仓库自包含

**原缺口**: 4 张大表(约 64 MB)与生成的 `enterprise.db`(约 88 MB)不入 git 历史 ⇒ 第三方 clone 后无法重建主库,评测与演示不可复现 —— 这是上轮「工程质量」的唯一扣分项。

**本轮改动(零引擎改动, 仅新增发布件与文档)**:

| 交付 | 内容 |
|---|---|
| Release [`dataset-v1`](https://github.com/congxinjie/agentic-text2sql/releases/tag/dataset-v1) | 5 个附件: `enterprise.db`(91,914,240 B) + 4 张大表 CSV(合计 66,828,070 B)；说明里逐个列出 sha256 |
| `scripts/fetch_dataset.sh`(新增) | 一键抓取 + 双校验。`gh` 已登录走 `gh release download`；否则走 `curl + REST API`(需 `GH_TOKEN`)。四种模式: `--db-only` / `--csv-only` / `--rebuild` / `--check` |
| `SHA256SUMS`(新增, 入库) | 5 个文件的 sha256 清单，脚本用 `sha256sum -c --ignore-missing` 比对 |
| README | §「数据说明」与 §「两个数据库」由"clone 后无法重建"改为"一条命令补齐"；§CI 边界说明同步改写(CI 仍**不**下载附件, 保持零联网) |

**机器证据(本机实跑)**:

```
① 附件核验   gh api releases/tags/dataset-v1 → 5/5 附件的 size 与 digest(sha256) 与本地逐一相等
② 干净环境   /tmp 空目录 + 只有 scripts/ 与 SHA256SUMS(无任何数据文件)
             bash scripts/fetch_dataset.sh --db-only
             → 下载 88MB + sha256 OK + 库内容校验(8 表 / 831,447 行 / 7 索引)全绿, 退出码 0, 15.2s

             → 与 Release 的 enterprise.db 逐表逐行内容哈希全等(8/8 表、831,447 行、DDL 与 7 索引相同)
               文件级 sha256 不同仅为 SQLite 物理页布局差异, 属正常
④ 零引擎改动 本轮只新增 scripts/fetch_dataset.sh、SHA256SUMS 与文档 + 建 Release; text2sql.py 等引擎文件未被触碰
```

**为何补这 1 分**: 上轮工程分的唯一缺口是「仓库不自包含」。现在第三方照 README 走三步(clone → `bash scripts/fetch_dataset.sh` → `python3 benchmark/run_eval.py`)即可在本机复现全部评测与演示,每一步都有 sha256 与行数校验兜底,不再依赖口头说明。

## 6. 本轮增补记录(2026-10-06): 引擎补「实体」独立字段与程序化校验(M13)

**原缺口**: 命题要求"识别用户意图、**实体**、维度、指标和筛选条件", 而五要素里只有「实体」既无独立字段也无校验器
(`docs/算法说明.md` 术语表原样标注"未实现") —— 评委逐项对照时唯一对不上号的一条。

**本轮改动(引擎纯增量 166 行, 未重写)**:

| 交付 | 内容 |
|---|---|
| 计划键 `entities` + `Answer.entities` | 每项 `{name, table, key, evidence, source}`, `source ∈ explicit/implied` |
| 词表注入 `biz_context.entities` | 引擎零硬编码 → CI `decouple` 仍绿 |
| `_extract_entities` / `_enforce_entity_contract` / `_check_entities` | 纯程序化抽取(explicit 问题直指 / implied 计划隐含)、契约兜底(不实声明丢弃并记 `entities_notes`)、五项校验 |
| 输出面 | Trace 增「识别实体」阶段; CLI 打印 `[实体]`; `demo/server.py` 与 `app_core.py` 响应带 entities; run JSON 逐题留档 + 报告 §1b 统计 |
| `ci_check.py` 第 9 项 `entities` | 正例 + **四个负对照(错表/错列/假 explicit/漏识别)** + **断言"注入词表前后计划提示词逐字相同"** |

**关键设计决定: 词表不进提示词** —— 最初把词表拼进计划提示词, 小样本(S09/S10/C08 各 2 次)看似会带动模型多 JOIN 承载表;
去掉提示词复查后同一 JOIN 变体仍出现 ⇒ 判定为 **LLM 固有抖动**(与 M10 自身两跑仅 30/40 逐字相同同源), 与词表无关。
仍然选择不拼, 因为这样"实体识别不影响计划"成为**可断言的不变量**(CI 断言), 不必靠抽样去论证"无影响"。

**机器证据(本机实跑)**:

```
① ci_check.py 9 项全绿; 新增第 9 项自带四个负对照 + 提示词不变量断言
② 40 问全量真实重跑(deepseek-chat, 双跑):
   跑A  e2e 100.0% / exec 100.0% / 口径 100.0% / 幻觉 0.0% · P50 8.244s P90 11.525s
   跑B  e2e 100.0% / exec 100.0% / 口径 100.0% / 幻觉 0.0% · P50 7.977s P90 10.907s
   实体覆盖 跑A 39/40 · 跑B 39/40; 实体项 跑A 47(explicit 45/implied 2) · 跑B 47(45/2)
   实体名分布 跑A {'客户': 33, '产品': 9, '营业部': 5} · 跑B {'客户': 33, '产品': 9, '营业部': 5}
   无实体的题(跑A ['M10'] / 跑B ['M10'])是"账户维度"类问题: 问题原文与计划里都没有实体, 规则 e 如实声明 covered=false

   与 M10 基线 SQL 逐字相同 跑A 17/40 · 跑B 19/40(相似度中位 0.991/0.998, 最低 0.575/0.501);
   对照 M10 自身两跑只有 30/40 逐字相同(相似度最低 0.475) ⇒ 文本差异属 LLM 固有抖动。
   真正的判据在结果层: 两跑均 40/40 对金标全对; 与 M10 结果集一致 跑A 39/40 · 跑B 39/40
   (唯一差异 C02 是"客户数/盈亏合计"两列顺序交换, 判定均正确)
④ 不注入词表(entities=None)时: 计划提示词逐字不变、计划不加 entities 键、无「识别实体」阶段、Answer.entities 恒为空
```

**评分口径**: 五维自评不变(工程质量已在 20/20 上限; 其余三档未动)。补的是"命题五要素逐项可对上号"——
