# 评测口径定义(M1)

> 状态:待队伍确认。本文档把 COMPETITION.md §6 落成可执行、可复算的评测口径;M2 的评测 runner 与基准集严格按本文档实现。评测数字必须来自真实运行,禁止估算或编造(铁律 6)。

---

## 1. 总则

- **评测对象**:`QueryAgent`(text2sql_demo/text2sql.py)以 `biz_context=` 注入企业语义后,对 `Agentic智能问数在客户营销场景的应用数据集/enterprise.db` 作答。
- **模型**:DeepSeek `deepseek-v4-flash`(环境变量 `LLM_BASE_URL`/`LLM_MODEL` 可替换,不设私有化适配时用默认)。每问调用参数与耗时均记录。
- **库只读**:评测全流程 `mode=ro + PRAGMA query_only=ON`(引擎既有),不得写库。
- **基准集自建,不依赖 `Q&A.xlsx`(空壳)**。所有标准答案由人工标注 + 在库上真实运行验证。
- **人工复核**:结果正确率/口径正确率以人工标注为准;能规则化的判定交给 runner,不能的走人工复核表(留痕)。

## 2. 指标定义(COMPETITION §6.1 落地)

设基准集共 N 问。对每一问,runner 记录 `exec_ok`、`result_ok`、`caliber_ok`、`hallucination`、`elapsed_ms`。

### 2.1 SQL 可执行率
```
SQL可执行率 = |{i: exec_ok_i}| / N
exec_ok = 生成 SQL 通过安全校验 且 执行成功
```
- 安全校验 = 单条语句 + 只读(SELECT/WITH 主动词解析)+ 剥离注释(引擎 `_validate`)。
- 执行失败后自动修复一次成功,仍记 `exec_ok=True`(说明修复路径是否生效,在日志单独统计"修复率")。

### 2.2 结果正确率
```
结果正确率 = |{i: exec_ok_i ∧ result_ok_i}| / N
```
- 单值/数值类:与标准答案数值比较,相对/绝对容差 1e-6(按标准答案标注方式)。
- 分组/多行类:先按行集比对(行数 + 分组键集合),再比对聚合值(容差 1e-6);顺序无关。
- 明细类:行数 + 抽样/集合比对(排序后全量比对,过大时抽主键集合比对并注明)。
- `result_ok` 的判定数据由 runner 输出,人工复核确认后入报告。

### 2.3 口径正确率
```
口径正确率 = |{i: exec_ok_i ∧ caliber_ok_i}| / N
```
- `caliber_ok`:Agent 结论引用的时间范围、统计定义、默认假设与标准答案"期望口径"一致。
- 判定方式:规则优先(时间范围正则、账户维度 nm/fc、币种 ccy、公式模板匹配);规则覆盖不了的走人工复核表。

### 2.4 端到端准确率(参赛口径,目标 ≥90%)
```
端到端准确率 = |{i: exec_ok_i ∧ result_ok_i ∧ caliber_ok_i}| / N
```

### 2.5 幻觉率(目标趋近 0,分项报告)
```
幻觉率 = |{i: hallucination_i}| / N
```
- 判定:引用库中不存在的表/列(结构化比对 `get_table_meta`)、引用不存在的指标/口径(与指标/口径字典比对)、或结果凭空编造(SQL 结果与库内重算不一致且非容差问题)。
- 报告分三小项:表/列幻觉、指标口径幻觉、结果幻觉。

### 2.6 耗时(目标:简单/中等/复杂均分钟级)
- 每问记录端到端 `elapsed_ms`(从提问到解释完成)。
- 报告 `P50/P90/MAX`(简单/中等/复杂分组分别给),单位秒。

## 3. 基准集自建规范(COMPETITION §6.2 落地)

### 3.1 规模与难度分布
- 默认 **40 问 = 简单 14 / 中等 14 / 复杂 12**(决策点 10.2 的默认值,待队伍确认后锁死)。
- 难度分级:
  - **简单**:单表、单指标、单筛选(可含一个时间条件);如"2026-03-31 各风险等级客户数"。
  - **中等**:join(含 dim_public 解码 / dim_product 分类 / dim_branch 层级)、多条件、时间范围;如"Q1 交易过招商银行的客户,期未还持有中国平安的有多少"。
  - **复杂**:多层聚合/窗口/多快照对比/口径易混(盈亏、日均、客群交集);如"钻石卡男性 40 岁以上、Q1 末持比亚迪>1000 的客户 Q1 盈亏"。

### 3.2 题目来源与覆盖
- 来源:表描述.sql 业务含义 + dim_public/dim_branch 字典 + 营销场景(客户分层/持仓/交易/盈亏/资产/资金流/营业部分布),覆盖三类:**客户筛选、指标查询、数据分析**。
- 必覆盖维度(与元数据方案对齐):编码解码(等级/性别/学历/职业)、产品分类(二级/一级)、时间口径(客户 20260531 快照 vs 2026-Q1 事实)、账户口径(nm/fc)、币种(ccy)、盈亏口径、营业部层级、脱敏不越界。

### 3.3 文件格式
- 位置:`benchmark/benchmark.json`(UTF-8;字段顺序固定;可另给 CSV 副本便于人工复核)。
- 每条记录:

```json
{
  "id": "Q001",
  "question": "各客户等级分别有多少客户?",
  "difficulty": "medium",
  "category": "客户筛选",
  "tables": ["ads_cust_info_d", "dim_public"],
  "gold_sql": "SELECT p.describe AS 客户等级, COUNT(*) c FROM ads_cust_info_d a JOIN dim_public p ON a.cust_lvl_cd=p.code AND p.code_type_id='100' WHERE a.data_dt='20260531' GROUP BY p.describe ORDER BY c DESC;",
  "gold_answer": {"type": "grouped", "rows": [["紫金理财银卡客户", 151], ["紫金理财金卡客户", 118]], "tolerance": 1e-6},
  "caliber_notes": "客户表只有 20260531 快照;客户等级经 dim_public code_type_id=100 解码(cust_lvl_cd);注意:库中无任何表引用 400 风险等级,风险等级类问题按不可答处理。",
  "scenario": "normal"
}
```

### 3.4 标注规则(人工标注,必须留痕)
1. `gold_sql` 必须在库上真实跑通,`gold_answer` 由该 SQL 真实输出并经人工确认口径后填写(禁止估算)。
2. 每问标注 `caliber_notes`:期望口径的完整说明(时间/账户/币种/公式/默认假设),供口径正确率判定。
3. 每问标注 `scenario`(见 §4 场景枚举,正常/异常两类)。
4. 标注完成后抽 3 题双人复核(队伍内互查),差异记录进 `benchmark/标注复核记录.md`。
5. 口径红线:库内无任何表引用 300 证件 / 400 风险等级码,此类业务问题标注为不可答(E4 场景),不得硬凑映射;如需映射到客户等级,由队伍先定口径再入集。

## 4. 异常与边界场景(COMPETITION §6.3 落地)

runner 正常题之外,单独建边界用例集 `benchmark/edge_cases.json`,每种场景 ≥1 个可复现用例。每用例标注:输入、预期行为、通过判据。

| # | 场景 | 预期行为(引擎现状) | 通过判据 |
|---|---|---|---|
| E1 | 正常查询 | 9 阶段走通,出 SQL+结果+解释 | exec_ok 且 result_ok |
| E2 | 缺信息可默认(仅缺时间范围) | 用默认口径(如最新快照/全区间)继续,解释注明假设 | caliber_ok(含假设说明) |
| E3 | 缺必填信息(指标不明) | 交互模式追问;非交互(评测)按 clarify=False 转默认假设并注明 | needs_clarification 或结论注明假设 |
| E4 | 不可答(闲聊/库外概念/主观建议) | 理解阶段 answerable=false,拒绝并给原因,不生成 SQL | 拒绝且 reason 合理 |
| E5 | SQL 生成错 → 自修复 | 执行失败 → 回传错误修复一次 → 成功 | 修复后 exec_ok;Trace 记录修复 |
| E6 | 修复后仍失败 → 兜底报错 | 报错信息友好,不崩溃,Trace 落 FAIL | error 非空、Trace 有 FAIL |
| E7 | 空结果 | 检查结果阶段提示"可能筛选过严/该时间段无数据",解释说明 | 结论含空结果说明 |
| E8 | 结果超限截断 | 展示前 MAX_ROWS 行并注明截断;解释注明基于前 N 行 | truncated 标志与说明 |
| E9 | LLM 网络/API 故障 | 阶段异常被 _safe_stage 捕获,返回友好错误,Trace 落 FAIL | 不崩溃、error 含原因 |

> E2/E3 的口径判定依赖 §3.4 的 `caliber_notes`;E4/E6/E9 的判定以 Trace 状态为准。

## 5. 评测 runner 输入输出规范(M2 实现,先锁格式)

- 输入:`benchmark/benchmark.json`(正常题)+ `benchmark/edge_cases.json`(边界题)+ `biz_context`(由 `benchmark/metadata/` 生成)。
- 逐题流程:加载基准集 → 构造 `QueryAgent(db=enterprise.db, biz_context=..., verbose=False)` → `agent.run(question, clarify=False)`(评测模式不交互)→ 采集:
  - `trace`(9 阶段状态/耗时/细节)、`sql`、`rows`、`explanation`、`error`、`elapsed_ms`;
  - 用 `gold_sql`/`gold_answer` 做结果判定,用 `caliber_notes` 做口径规则判定。
- 输出:
  - `benchmark/runs/run_YYYYMMDD_HHMMSS.json`(逐题明细,含判定字段与 Trace 摘要);
  - `benchmark/runs/run_YYYYMMDD_HHMMSS.md`(人工复核视图:问题/标准/实际/判定);
  - 汇总指标 JSON(`metrics.json`:六个指标 + 分难度耗时)。
- 复现性:README 写明重跑命令;每轮输出带时间戳与模型名。

## 6. 报告格式(M2 基线 / M5 最终)

`docs/评测报告-基线.md` 与 `docs/评测报告-最终.md` 统一章节:
1. 评测环境(模型/密钥来源/库指纹/机器/时间)
2. 指标汇总表(六指标 + 分难度)
3. 分难度/分场景明细(表 + 失败案例剖析)
4. 异常场景对照表(§4 的 E1–E9 逐项通过情况)
5. 失败根因分析与改进项(对接 M3)
6. 与目标对比(端到端 ≥90%;耗时分钟级;幻觉率趋近 0)
7. 复现步骤

## 8. 规则变更记录(M3,随评测重跑同步更新)

- **R1(2026-09-05)** 口径启发式修正:`expect_tables` 全属于单快照/纯维度表(`ads_cust_info_d`/`dim_public`/`dim_branch`/`dim_product`)时,豁免 `data_dt` 字面量检查。理由:客户主档仅一个快照,Agent 省略 `WHERE data_dt='20260531'` 属合理口径,不应判错。
- **R2(2026-09-05)** 结果比对修正:数值类以 gold 的小数位数为准,先四舍五入再比较(修复 `AVG` 未 ROUND 与 `ROUND(...,4)` 的对齐问题),1e-6 相对容差兜底;分组标签规范化(去掉"岁"与空白,修复 `30-50` vs `30-50岁` 类标签差异)。
- **R3(2026-09-05)** 分级模型策略:空响应实验证明 deepseek-v4-flash 在复杂题上大量返回空串(强提示重试无效,exec 4/13),而 deepseek-chat 复杂题 exec 13/13。故 runner 对复杂题默认 `deepseek-chat`,简单/中等保持 `deepseek-v4-flash`;可用环境变量 `LLM_MODEL` 整体覆盖。
