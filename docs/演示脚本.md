# 演示脚本（M8 本地演示层 · 3–5 分钟分镜）

> 面向对象：非技术评委。演示入口是 `demo/server.py`（纯标准库本地服务）+ `demo/index.html`（中文单页）。
> 数据只读；口径经 `--biz-context demo/enterprise_biz.json` 注入，演示层不内嵌口径；API key 只在服务端读取，不进前端。

## 0. 启动（演示前 1 分钟）

```bash
# 首次: 拉取主库(公开 Release 匿名直链 + sha256/库内容校验; 约 88MB)
bash scripts/fetch_dataset.sh --db-only

# 正式演示(需 LLM_API_KEY, 完整问答)
python demo/server.py --db "Agentic智能问数在客户营销场景的应用数据集/enterprise.db" \
                      --biz-context demo/enterprise_biz.json --port 8000

# 无密钥界面冒烟(只演示界面/阶段进度, 提问会明确报错, 不发起网络调用)
python demo/server.py --db customer_marketing_db/marketing.db --offline
```

浏览器打开 `http://127.0.0.1:8000`。看到中文单页：顶部一句话说明、问题输入框、示例问题 chips。

## 1.1 边跑边讲阶段（M10 等待期话术）

提问后界面顶部会出现**九阶段进度条 + 已用秒数计时器**（`demo/index.html` 走 `EventSource` 消费
`GET /api/ask/stream`，引擎每进入/结束一个阶段就推一条事件）。等待的 6–12 秒不要干等，按下面的话术
把"看得见的进度"讲成"看得见的方法论"（每条台词对应进度条正亮起的那个胶囊）：

| 亮起的阶段 | 台词（照着念即可） | 顺带指出的加分点 |
|---|---|---|
| 理解问题 | “先看它**怎么理解**我的话：抽出指标、维度、筛选和时间范围。” | 自然语言理解，不是关键词匹配 |
| 检索相关表和字段 | “接着它去**元数据**里找该用哪几张表、哪几个字段——只在这些表里取数。” | 元数据组织（AI 友好） |
| 生成查询计划 | “然后**先出计划、再写 SQL**：表、聚合、分组、排序都在计划里。” | 计划可解释、可检查 |
| 检查查询计划 | “计划还要过一遍**程序化检查**：表和字段必须真实存在，口径断言不通过就打回重规划。” | 安全围栏（防幻觉） |
| 生成SQL | “计划没问题，才生成 SQL。” | 先计划后 SQL，可控 |
| 安全校验 | “SQL 出来先过**安全校验**：只放行单条 SELECT/WITH/EXPLAIN，注释剥离，库还是只读打开的。” | 安全合规 |
| 执行 | “只读执行；万一报错，会进入**自动修复**再试一次——进度条上那一格会变色。” | 失败自修复、兜底 |
| 检查结果 | “结果表头要和计划声明的输出列对得上，缺列也会触发一次修复。” | 结果合法性校验 |
| 解释结果 | “最后把结果翻译成人话，讲清口径和默认假设。” | 输出可解释 |

收尾一句（计时器停下时）：**“您看，等待不是黑箱——计时器一直在走，每亮一格就是引擎真实走过的一步；
总耗时 X 秒，其中第一次阶段事件在 Y 秒内就到了。”**

> M13 起引擎还会追加一个「识别实体」阶段（前端动态追加到进度条/轨迹）；问题含实体时可在该阶段补一句
> “实体的抽取是程序化的，模型只负责规划，声明了词表外的实体或没落到计划里一律会被丢掉”。

## 3. 演示问答接口（无头可验证）

```bash
# 健康检查
curl -s http://127.0.0.1:8000/api/health

# 问答（POST JSON; GET 也支持 ?q=...&clarify=false）
curl -s -X POST http://127.0.0.1:8000/api/ask \
  -H "Content-Type: application/json" \
  -d '{"question":"各客户等级分别有多少客户?","clarify":false}'
```

返回 JSON 含：`question` / `answerable` / `sql` / `headers` / `rows` / `explanation` /
`plan` / `caliber_assertions` / `trace` / `error` / `elapsed_s` / `model`。
`trace` 中 `WARN`/`FAIL` 记录即为失败自修复过程。

**流式接口（M10，等待期反馈用）**：

```bash
# SSE: 每条 data: 是一段阶段事件; 最后一条是终止事件(内含完整结果, 字段与 POST /api/ask 相同)
curl -sN "http://127.0.0.1:8000/api/ask/stream?q=%E5%8D%8E%E4%B8%9C%E5%9C%B0%E5%8C%BA%E6%9C%89%E5%A4%9A%E5%B0%91%E5%AE%A2%E6%88%B7%3F&clarify=false"
```

- 阶段事件：`{"type":"stage","seq":1,"stage":"理解问题","status":"RUNNING","ts":…,"elapsed_s":0.01}`
  —— `status` 取 `RUNNING`(阶段开始) / `OK` / `WARN` / `FAIL`(阶段结束)。
- 终止事件：`{"type":"done","seq":…,"ts":…,"result":{…}}`，`result` 与 `POST /api/ask` 的响应逐字段相同。
- 事件里**只有阶段名/状态/序号/时间戳/耗时**，不含 SQL 片段、结果值与密钥；库为空时会给 400。
- 前端(`demo/index.html`)用原生 `EventSource` 消费它；流式失败/超时会自动回落 `POST /api/ask`。
