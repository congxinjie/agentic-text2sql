# 模型/算法说明

> 关联:COMPETITION.md 成果物 #5;覆盖 NLU/SQL 生成/校验/修复各环节的方法、实现与参数。

## 1. 总体架构

9 阶段状态机(见 text2sql.py docstring):理解 → 检索 → 计划 → 检查计划 → 生成 SQL → 安全校验 → 执行 → 检查结果 → 解释。每阶段输出写入 Trace;LLM 阶段异常经 `_safe_stage` 兜底为友好错误,不崩溃。

## 2. NLU(阶段 1 理解)

- 方法:单次 LLM 结构化抽取,输出 JSON:`answerable / summary / metrics / dimensions / filters / time_range / assumptions / missing(required|optional) / question_specificity(clear|vague)`。
- JSON 解析:`extract_json` 容错(剥 markdown、正则兜底);失败重试 1 次并带"精简输出"提示。
- 追问判据(程序化,不依赖 LLM 兜底):clarify=True 且 (missing_required 非空 **或** question_specificity=vague **或** 指标/维度/筛选/时间全空) → 强制 needs_clarification;E2 路径(有明确指标)不受影响。

## 3. 检索与计划(阶段 2-4)

- 检索:LLM 挑选相关表列,程序化校验表/列真实存在(库元数据 `get_table_meta`)。
- 计划:LLM 输出 tables/joins/filters/aggregations/group_by/order_by/limit/steps,**以及 M6 新增的结构化输出契约字段**:
  - `output_columns`:结果应展示的列(维度列/指标列/客户标识列),标量题只允许 1 列;客群筛选后再求指标合计时程序化要求"客户数+指标列"。
  - `dimension_labels`:每个维度的展示字段(编码维度优先 `describe`,不用 `code`;产品分类维度才同时输出 ID+名称)。
- 检查计划(程序化):计划表必须存在;"表.列"引用必须真实;每个维度/指标必须体现在计划文本;时间范围必须体现;有指标必须有聚合;**M6 新增**:`output_columns`/`dimension_labels` 缺失或字段不实、标量题多列、排名题误加客户数、口径断言不满足,均拒绝本次计划并自动重规划一次。
- **口径断言(M6,可配置)**:`QueryAgent(..., caliber_assertions=[...])` 注入通用规则 `{"id","when","must_contain","must_not_contain","desc"}`;`when` 全部命中问题/计划文本时检查计划文本,违反即拒绝重写。规则内容(份额 vs 市值、交易额=buy_amt+sell_amt、分类 LIKE、盈亏口径)由评测 harness 注入,不进引擎。

## 4. SQL 生成(阶段 5)

- 单次 LLM 生成一条只读 SQL;温度 0;`max_tokens=2800`(长 WITH 不截断)。
- **M6 输出列硬约束**:把计划 `output_columns`/`dimension_labels` 写入生成提示,要求结果表头逐字包含声明列;生成后程序化检查 SQL 文本是否含声明列,缺失则带反馈重写一次。
- 生成提示另含通用约束:SELECT 输出列严格等于 `output_columns`(禁止期初/期末、买入/卖出等中间列);禁止 CROSS JOIN;跨表合计先按客户分组聚合再用 LEFT JOIN + COALESCE 汇总,保证不漏客户。
- **sql_hints 机制(M3.7)**:按关键词触发的 few-shot 口径示例注入生成提示。引擎仅提供通用机制(`QueryAgent(db_path, api_key, biz_context, sql_hints, sensitive_columns)`),券商口径示例由调用方注入(benchmark/run_eval.py 的 SQL_HINTS:持有→份额、增幅→绝对增量、科创→LIKE+分公司、盈亏→LEFT JOIN 口径)。
- 提示约束:单 SELECT/WITH/EXPLAIN;表列必须来自给定结构;维度与实体标识列必须进 SELECT;编码维度只输出业务名称(产品分类维度才同时输出 ID+名称)。

## 5. 安全校验(阶段 6)

- 剥离注释(`--`、`/* */`);按分号切分语句(字符串字面量内分号不切);拒绝多语句。
- 仅放行 SELECT/WITH/EXPLAIN 开头;`WITH` 解析 CTE 后主语句动词(`_with_main_verb`),拒绝 `WITH ... DELETE/UPDATE/INSERT`。
- 执行层双保险:`file:...?mode=ro` + `PRAGMA query_only=ON`。
- **SQL 编译器前端(AST, `sql_ast.py`)**: 词法 + 语句结构解析; `_ast_check` 做 AST 级只读/真实表列校验(错表/错列/`WITH` 后写语句均拒); CI 第 10 项 `sql-ast`(46 金标全可解析 + 负对照)。
- **输出列投影(结果层)**: `_project_result` 在计划声明列齐全时, 把结果多出的列确定性裁剪到声明列, 修掉 LLM 多输出列抖动。

## 6. 执行与修复(阶段 7)

- 只读执行,单问最多取前 100 行(截断标注)。
- 执行失败自动修复一次:把 SQL + 问题描述回传 LLM,输出修正 SQL 再执行;再失败则兜底报错并记录 Trace FAIL。
- **M6 结果列修复**:执行成功后,`_check_result` 校验"计划 `output_columns` 是否都在结果表头";缺失列复用同一 `_repair_sql` 机制修复一次(把缺失列作为问题描述回传 LLM 重写 SQL),再执行一次。
- **查询计划分析**: 执行成功后只读跑 `EXPLAIN QUERY PLAN`(不取数据), 把全表扫描/索引命中记入 `Answer.query_plan`; 含全表扫描时结果检查给出提示。

## 7. 结果检查与解释(阶段 8-9)

- 结果检查(程序化):空结果(提示筛选过严/无数据)、单行、截断(注明前 N 行)、**计划声明列缺失(M6,触发一次修复)**。
- 解释:LLM 基于 问题+SQL+结果(前 20 行)+检查备注+默认假设,输出 3-6 句中文结论(结论先行、关键数字、假设与局限说明)。

## 8. 参数与模型
