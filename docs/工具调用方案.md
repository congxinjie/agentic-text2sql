# 工具调用方案

> 关联:COMPETITION.md 命题原文(2)成果形式"**工具调用方案**"。
> 本文只描述**已经存在**的能力,行号均指 `text2sql_demo/text2sql.py`(全文 1355 行);凡命题提及但当前未实现的,一律显式标注「**未实现**」。
> 代码与文档的一致性抽查命令见文末 §7。

## 0. 一句话概括

引擎把"一个动作"封装成一个工具,并按**能力来源**分成两类:

- **LLM 工具**(理解 / 检索 / 计划 / 生成 SQL / 修复 SQL / 解释)—— 负责"**说不算数**"的语义推测,输出一律走 JSON 或裸 SQL 文本,由程序化工具复核后才采信;
- **程序化工具**(SQL 校验器 / 计划校验器 / 输出列契约兜底器 / 结果校验器 / 只读执行器)—— 负责"**说了算**"的事实判定,零 LLM、零第三方依赖。

设计原则:**凡是能被程序判定的事实(表存在吗、列存在吗、是不是只读、结果里有没有声明的列),绝不做成 LLM 提示词里的"请你注意"**。

## 2. 每个工具的输入 / 输出契约

### T1 理解器(`:675`)

- **输入**:`system=UNDERSTAND_SYS`(`:524` 起);`user = _ctx() + 用户问题 + "请输出 JSON"`(`_ctx()` 为 库结构 + 业务说明,`:671`;组装在 `:677-679`)。
- **输出 JSON 键** → 逐字段落到 `Understanding` dataclass(`:487-498`):

| JSON 键 | 落地字段(行) | 说明 |
|---|---|---|
| `answerable` | `answerable` `:488` | false ⇒ 越界/不可答,直接拒绝(`:1190-1193`) |
| `reason` | `reason` `:489` | 不可答原因文本 |
| `summary` | `summary` `:490` | 一句话重述**用户意图**,下游检索/计划 prompt 均以它作为"意图"字段(`:730`、`:761`) |
| `metrics` | `metrics` `:491` | 想算的指标 |
| `dimensions` | `dimensions` `:492` | 想按什么分组 |
| `filters` | `filters` `:493` | 自然语言筛选条件 |
| `time_range` | `time_range` `:494` | 单独抽出的时间范围 |
| `assumptions` | `assumptions` `:495` | 默认假设,最终进解释 |
| `missing`[{`item`,`required`}] | `missing_required` `:496` / `missing_optional` `:497` | required=true 触发追问(`:1195`);`missing` 的拆解循环在 `:697` 起 |
| `question_specificity` | `question_specificity` `:498` | vague 触发程序化追问(`:1201`) |

- **容错**:数组里出现非 dict 项时降级取串(`:681-684`)。

### T2 检索器(`:727`)

- **输入**:`_ctx()` + 问题理解摘要(意图/指标/维度/筛选/时间,`:728-733`)。
- **输出 JSON**:`{"tables": [{"table": str, "columns": [str], "why": str}]}`(`RETRIEVE_SYS` `:545-553`)。
- **程序化收敛(输出不直接采信)**:表名必须命中 `self.meta`,未命中丢弃并记 note(`:739` / `:749`);列名必须命中 `meta[表]`,未命中剔除并记 note(`:747`);结果去重保序(`:750`)。

### T3 计划器 / T3' 重规划器(`:759` / `:891`)

- **输入**:`_ctx()` + 问题理解 + **T2 已检索的表字段带列清单**(`:761-767`);`T3'` 另加 原计划 JSON + V2 的 issues 列表(`:893-896`)。
- **输出 JSON 键**(`PLAN_SYS` `:555-585`):`summary`、`tables`、`joins`、`filters[{field,op,value,desc}]`、`aggregations[{func,field,alias}]`、`group_by[{expr,alias}]`、`order_by[{expr,dir}]`、`limit`、`steps[]`、**`output_columns[{name,desc}]`(必填)**、**`dimension_labels[{dimension,code_field,label_field}]`(有维度分组时必填)**。

### T4 SQL 生成器(`:966`)

- **输入**:`_ctx()` + 问题/指标/维度/筛选/时间/假设 + 计划 JSON + V2 的未解决 issues + 四条通用 SQL 约束(禁 CROSS JOIN、跨表合计先按客户分组再 LEFT JOIN + COALESCE,`:978-979`);**追加三块硬约束**:声明列必须逐字出现在结果表头(`:980-983`)、维度展示字段约束(`:984-991`,编码维度只输出解码名)、**命中的 `sql_hints` 口径示例**(`:993-997`)。
- **输出**:**裸 SQL 文本**(非 JSON),`max_tokens=2800`(`:999-1001`)。
- **后置**:声明的列未出现在 SQL 文本中 ⇒ 带反馈重写一次(`:1002-1013`)。

### T4' SQL 修复器(`:1068`)

- **输入**:原 SQL + `problem`(异常对象或文字描述,`:1071`)+ 问题 summary + 计划 JSON(`:1072-1077`)。
- **输出**:裸 SQL,且**必须重新过 V1**(`:1080` `validate_sql`)。
- **两个调用方**:执行失败(`:1245`)与结果缺列(`:1259-1266`),即"同一修复机制,两种触发"。

### T5 解释器(`:1121`)

- **输入**:问题 summary + 已执行 SQL + 结果**前 `EXPLAIN_MAX_ROWS`(=20,`:53`)行** + V4 的检查备注 + 默认假设(`:1131-1137`)。
- **输出**:3~6 句中文文本;空返回 ⇒ 兜底文案 `FALLBACK_EXPLANATION`(`:112`,判定在 `:1139-1142`)。

### E1 只读执行器(`:438`)

- **输入**:`db_path` + 已过 V1 的 SQL。
- **输出**:`(headers, rows, truncated)`(`:449`);最多取 `MAX_ROWS`(=100,`:52`)行,多出即 `truncated=True`(`:447-449`)。
- **只读**:连接串 `file:{db}?mode=ro`(`:440`)+ `PRAGMA query_only=ON`(`:442`);语句不产生结果集直接报错(`:444-445`)。

### V1 SQL 校验器(`:417`)

- **输入** SQL 文本;**输出** 归整后的 SQL,或抛 `ValueError`(调用方据此终止本次问答,`:1232-1235`)。
- 子步骤:剥注释 `strip_comments` `:288` → 切语句 `split_statements` `:294`(字符串字面量内分号不切)→ 拒多语句 `:424` → 前缀白名单 `SELECT|WITH|EXPLAIN` `:427` → `WITH` 主语句动词解析 `_with_main_verb` `:349`,非只读即拒(`:434`)。

### V2 计划校验器(`:773`)

- **输入** 理解 + 检索 + 计划;**输出** `(ok, issues)`。九组检查(编号与代码注释一一对应,`:776` 起):
  4.1 计划引用的表必须真实存在 `:781`;4.2 `表.列` 引用必须真实 `:787`;4.3 每个维度必须体现在计划 `:792`;4.4 每个指标必须体现在计划 `:797`;4.5 时间范围必须体现 `:801`;4.6 有指标必须有聚合 `:805`;4.7 输出列必须结构化声明 `:818`/`:837` 与标量题单列 `:846`;4.7b 客群筛选后的"客户数"契约 `:825`/`:831`/`:834`;4.8 `dimension_labels` 必须存在且字段真实 `:850`/`:859`/`:863`;4.9 口径断言 `:868-882`。

### V3 输出列契约兜底器(`:933`)

- **输入** 理解 + 计划;**输出** 修订后的计划(**不调用 LLM**):排名/明细题误加"客户数"则剥离(剥离动作在 `:950`),客群筛选题缺"客户数"则补声明(补声明在 `:963`)。

### V4 结果校验器(`:1100`)

- **输入** headers / rows / truncated / 计划;**输出** `(notes, missing)`。空结果 `:1106`、仅 1 行 `:1108`、截断 `:1110` 各给提示;声明列缺失产出 `missing`(`:1114-1116`)并触发一次修复重跑(`:1259-1266`)。

## 3. 调用顺序与依赖

```text
用户问题
  └─ T1 理解器 ──→ answerable=false ⇒ 拒绝(围栏 §4)
       │            missing_required / vague ⇒ 追问
       ↓ Understanding
  └─ T2 检索器 ──→ 表/列逐字校验(丢弃幻觉表/列)
       ↓ Retrieval
  └─ T3 计划器 ──→ V2 计划校验 ──不过──→ T3' 重规划 ──→ V2 再检
       ↓ plan                                  (最多一轮)
  └─ V3 输出列契约兜底(程序)
       ↓ plan'
  └─ T4 SQL 生成 ──声明列缺失──→ T4 重写一次
       ↓ raw_sql
  └─ V1 SQL 校验 ──不过──→ 终止并报告        ← 围栏:SQL 合法性
       ↓ cleaned sql
  └─ E1 只读执行 ──失败──→ T4' 修复 ──→ V1 ──→ E1 重执行(一次)
       ↓ headers/rows/truncated
  └─ V4 结果校验 ──声明列缺失──→ T4' 修复 ──→ E1 重执行(一次)
       ↓ notes
  └─ T5 解释器 ──→ 中文结论 + 口径说明
```

**依赖关系(谁能读谁的产物)**:

| 工具 | 依赖的上游产物 | 说明 |
|---|---|---|
| `T1` | 仅库结构 + 业务说明 | 无状态 |
| `T2` | `Understanding` | 只读理解结果,不读库数据 |
| `T3` | `Understanding` + `Retrieval` | 只能在 T2 已检索的表列里做计划 |
| `V2` | `Understanding` + `Retrieval` + `plan` | 程序化,不调 LLM |
| `T4` | `plan` + V2 的 `issues` | 未解决项作为"请尽量规避"提示 |
| `V1` | `T4`/`T4'` 的 SQL | 唯一能放行 SQL 的关口 |
| `E1` | 仅接受 `V1` 放行的 SQL | 由 `_run` 的调用顺序保证(`:1232` → `:1242`) |
| `V4` | `E1` 结果 + `plan.output_columns` | 比对"声明"与"实际表头" |
| `T5` | `E1` 结果 + `V4` notes + 假设 | 只解释,不再改 SQL |

**无跨调用会话状态**:每个 LLM 工具都是独立的无状态调用,各自重新拼 `_ctx()`(`:671`);唯一的跨调用信息传递是显式参数(`_replan` 带旧计划与 issues、`_repair_sql` 带旧 SQL 与问题描述)。状态机本体的顺序与兜底集中在 `QueryAgent._run` — `:1169`。

## 4. 重试与兜底策略

| # | 机制 | 触发条件 | 行为 | 代码位置 |
|---|---|---|---|---|
| R1 | **HTTP 指数退避** | HTTP 429/500/502/503/504,或 `URLError`/`TimeoutError` | `delay = 1.5 * 2**attempt`(1.5s → 3s),最多 `max_attempts=3`;仍失败抛 `RuntimeError`(带响应体前 500 字符) | `:153-154`、`:175-191` |
| R2 | **JSON 解析重试** | 无法解析为 JSON 对象,或输出是别的 JSON 类型 | 把错误信息 + 上次输出开头 200 字符塞回提示,**重试 1 次**(`:214` 的 `range(2)`);仍失败抛错 | `:212-231` |
| R3 | **计划重规划** | V2 返回 `ok=False` | `T3'` 带 issues 重新出计划一次,再跑 V2;两次都不过则以带 `issues` 的状态继续生成 SQL(不再无限重试) | `:1218-1221` |
| R4 | **生成期输出列重写** | SQL 文本里缺少 `output_columns` 声明的列 | 带"缺失列清单"反馈重写一次(`max_tokens` 仍 2800) | `:1002-1013` |
| R5 | **SQL 自修复** | 执行抛 `sqlite3.Error`/`ValueError`,或结果表头缺声明列 | `T4'` 修复 → 重新 `V1` → 重执行;**执行失败与缺列各只修一次**,再失败即 `ans.error` 终止 | `:1245-1252`、`:1259-1266` |
| R6 | **空返回兜底** | 解释文本为空 | 用 `FALLBACK_EXPLANATION`(`:112`)并记 WARNING(`:1139-1142`);`llm_chat` 对空内容只记 WARNING、**不改行为**(`:170-172`) | `:112`、`:1139-1142` |
| R7 | **阶段异常兜底** | 任一阶段抛 `STAGE_ERRORS`(`:99`:`ValueError/RuntimeError/TypeError/AttributeError`) | `_safe_stage`(`:1146`)记 FAIL 并抛出,`_run` 各段 `except` 转成友好 `ans.error`,**不崩溃、不返回半成品** | `:1146-1154`、`:1181`、`:1226`、`:1251`、`:1276` |
| R8 | **追问兜底** | 必填信息缺失且允许追问 | 不猜、不生成 SQL,直接返回 `needs_clarification` | `:1195-1197` |

**兜底优先级**:能自动修的程序化修(计划→V2→T3'、缺列→T4')> 修不了就降级报告(WARN note + 结论里说明)> 实在不行才终止(`ans.error`)。全程写入 `Trace`(`:463`)与轮转日志。

## 5. 引擎不持有业务域知识:口径经注入侧传入

### 5.1 三个注入口(`QueryAgent.__init__` — `:597`)

| 注入口(参数) | 默认值 | 内容 | 落地行 |
|---|---|---|---|
| `biz_context` | `BUSINESS_DESC`(银行营销库语义,`:115`) | 业务说明文本,拼进每个 LLM 工具的 `_ctx()` | 参数 `:598`、赋值 `:605`、拼接 `:671-672` |
| `sql_hints` | `{}` | 关键词 → few-shot 口径示例,命中即注入生成提示 | `:607`、命中逻辑 `:993-997` |
| `caliber_assertions` | `[]` | 口径断言规则 `{"id","when","must_contain","must_not_contain","desc"}`,V2 逐条检查 | `:610`、检查 `:868-882` |

调用方(评测 harness / 演示层)按库切换这三者即可换域;引擎侧 0 改动。

### 5.2 为什么这样切分

1. **引擎可迁移**:同一份 9 阶段状态机要接银行营销库、券商客户营销库、乃至任意 schema,差异只在"业务说明 + 口径示例 + 口径断言"三份数据。
2. **口径变更不必动核心代码**:改一条口径 = 改注入文件,不碰引擎、不重跑引擎逻辑回归。
3. **可机器验证**:`ci_check.py` 的 `decouple` 检查(`ci_check.py:252`)用"固定券商词表 + 从 `demo/enterprise_biz.json` 抽取的 token"断言引擎与演示层里**不出现**任何券商域词 —— 把"语义只走注入"从口头承诺变成 CI 里的红灯机制。
4. **评审可核对**:域词与口径集中在一份可读的注入文件里,评委逐条对照口径时不必翻引擎源码。

### 5.3 未实现 / 非目标(如实标注)

- **未实现**:引擎内**没有任何**业务词典、同义词表、实体词表或指标字典。"口径字典/维度字典"以文本形式存在于注入侧(`biz_context`、`sql_hints`),引擎不做结构化校验,也不内置任何域词。
- **未实现**:"实体"**没有独立的识别字段**。命题要求的"识别实体"当前由 `Understanding.summary`(意图)+ `T2` 检索到的表列 + 计划 `output_columns` 里的客户标识列 + 生成提示里"JOIN ON 关联键(以业务说明给出的客户标识/关联键为准)"共同间接承载(`:579`、`:582-583`、`:978-979`);详见 `docs/算法说明.md` 的「命题术语 ↔ 代码字段对照表」。
- **非目标**:本轮不引入工具注册表/插件化框架 —— 工具集合是固定的 9 阶段流程,不是开放式 Agent 工具市场。
