# 技术报告

> 参赛成果物 #3。八节:问题理解 / 技术路线 / 系统架构 / 核心算法 / 关键模块 / 实验设计 / 效果评估 / 不足分析。

## 1. 问题理解

客户营销业务人员要"客户筛选、指标查询、数据分析"时,传统路径依赖数据团队排期写 SQL,门槛高、周期长;自助 BI 学习成本高、口径易失控。本系统以**自然语言 → 只读 SQL → 数据表 + 可解释结论**为闭环,目标:执行准确率 ≥90%、简单/中等/复杂查询分钟级完成、显著减少大模型凭空生成表/字段/指标/结果(幻觉)。

目标用户:业务人员(提问看数)、数据分析师(口径复核/溯源)、运维(只读安全兜底)。

## 2. 技术路线

- 引擎:Python 标准库 + DeepSeek OpenAI 兼容端点,零第三方依赖(text2sql.py)。
- 架构:9 阶段状态机(理解→检索→计划→检查→SQL→安全校验→执行→结果→解释),全程 Trace 留痕;业务语义经 `biz_context`/`sql_hints` 注入,库与口径解耦(同一引擎可接任意 schema)。
- 评测:M2 起自建 46 问基准集(简单14/中等18/复杂14,gold_sql 全量真实跑通闸门)+ 评测 runner + 判定器(R1-R10),双跑取平均。
- 交互:M4 起 Streamlit 单页 UI + CLI 双入口。 演示层支持**图表(服务端生成 SVG 条形图)/CSV 导出**, 并可携带上一轮结论做**多轮下钻**; 零第三方依赖(纯标准库服务端 + 原生 JS)。
- 智能体多步(可选): `decompose_mode="auto"` 时, 多部分/复杂问题先由「任务分解器」拆成 2~3 个可独立执行 SQL 的子问题, 每个子问题独立走完整 9 阶段链路, 再由「结论合成器」汇总为最终结论; 任一子问题失败即回退单轮。默认 `off`, 不影响既有评测。

## 3. 系统架构

```
用户(UI/CLI)
   ↓
QueryAgent(9 阶段状态机)
   理解(NLU 结构化) → 检索(表列校验) → 计划 → 检查计划(程序化) → 生成SQL
   → 安全校验(只读三保险) → 执行(失败自修复一次) → 结果检查 → 解释
   ↑ 注入: biz_context(业务口径) + sql_hints(few-shot 口径示例)
数据: enterprise.db(只读; mode=ro + PRAGMA query_only)
评测: benchmark/{benchmark.json, run_eval.py, rejudge.py, average_runs.py}
```

## 4. 核心算法

见 docs/算法说明.md。要点:
- NLU:LLM 结构化抽取 + `question_specificity` 自评 + 程序化追问判据(防 LLM 把模糊问题默认化)。
- SQL 生成:温度 0、2800 tokens、few-shot 口径示例按关键词触发(sql_hints)。
- 校验:单语句只读 + `WITH` 主动词解析 + 计划层表/列真实性检查 + 结果合法性检查。
- SQL 编译器前端(纯标准库 `sql_ast.py`): 词法 + 语句结构 AST, 做 AST 级只读/真实表列校验, CI 第 10 项 `sql-ast`(金标全可解析 + 错表/错列/WITH 后写负对照)。 并在结果层按计划声明列做**输出列投影**(多余列裁剪), 把输出列契约变成确定性行为。
- 查询计划分析(纯标准库 `sql_plan.py`): `EXPLAIN QUERY PLAN` 不执行数据, 统计全表扫描/索引搜索/索引扫描/临时 B 树; 引擎每题记录 `Answer.query_plan`, 报告 §1d 汇总; `benchmark/query_plan_report.py` 产出 `docs/查询优化报告.md`。
- 数据库适配层(纯标准库 `db_adapter.py`): 数据访问收敛到 `table_meta/schema_text/run_query` 统一接口, 默认 `SqliteAdapter`(委托既有实现, 行为不变); MySQL/PostgreSQL 等由使用方注入 adapter(驱动不进引擎), 详见 `docs/数据库适配方案.md`。
- RAG schema linking(纯标准库 `schema_rag.py`, 可选): BM25 + 中文 bigram 从"表/列名 + `biz_context` 中文片段"召回 top-k 表; `QueryAgent(retrieve_mode="rag")` 时只注入召回表完整结构 + 其余表名/列名目录, `Answer.rag_tables` 落 Trace; 默认 `retrieve_mode="full"` 全量注入, 基线行为不变。46 问离线消融 top-6 召回 95.7%; CI 第 12 项 `schema-rag`(`benchmark/rag_ablation.py` 产出 `docs/RAG检索报告.md`)。
- 修复:执行失败回传错误修复一次;LLM 调用层超时/429/5xx 指数退避重试 ≤3 次(R9)。

## 6. 实验设计

- 基准集 46 问,难度 14/18/14;每条含 question/gold_sql/gold_answer(库内真实运行)/caliber_notes/expect_time/expect_tables。
- 判定六指标:SQL 可执行率、结果正确率(1e-6 容差,列名对齐)、口径正确率(规则启发式)、端到端准确率(参赛口径)、幻觉率、耗时 P50/P90。
- 双跑取平均(deepseek-chat 全量),判定器改动走"重判留档→回填"方法论,LLM 输出与判定器演进严格分离。
- E1-E9 异常边界用例独立复跑。

## 8. 不足分析

- **复杂题依赖长上下文口径遵守**:M3.7 时复杂题 79.2%(C02/C07 长提示下口径遵守瓶颈);经口径断言、输出列契约、sql_hints 后,M9–M13 与 2026-10-07/08 双跑复杂题均 100%。风险仍在:换模型/换库需重新标定与回归。
- **LLM 固有抖动**:同口径下 chat 输出逐轮抖动(列顺序、是否多带列、偶发空返回/长重试)。已用"温度 0 + 调用层重试 + 输出列契约 + 判定器对齐"压缩影响;2026-10-07/08 双跑均 40/40,但第二轮 S08 一次 96.8s 重试说明时延仍有长尾。
- **「意图」已补独立字段**:命题五要素中"意图"由 `Understanding.summary` + `question_specificity` 承载,已补 `Understanding.intent` 枚举 + 程序化兜底;「实体」M13 已补齐, 五要素逐项落地。
- **实体词表人工声明**:三张承载表由注入侧人工声明,未做"表→实体"自动发现;不注入词表时实体功能整体关闭(刻意保守设计)。
- **口径启发式边界**:规则式口径判定对"合理省略单快照过滤"仍依赖 R7 豁免表,极端改写 SQL 可能误判,已通过 rejudge 留档控制。
- **交互层**:已补图表(SVG)/CSV 导出/多轮下钻;但仍无真人浏览器可用性实测与移动端适配。
- **基准代表性**:46 问为自建基准,不等于生产分布;接真实数仓需重新标定、补权限与行级过滤。
- **UI 依赖**:Streamlit 为第三方依赖(requirements.txt 说明);引擎与本地演示层保持零第三方。
