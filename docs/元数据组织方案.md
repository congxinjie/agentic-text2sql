# 元数据组织方案(M1)

> 状态:待队伍确认。本阶段只定设计与格式,不写代码;M2 起按本方案生成结构化元数据文件并接入评测。
> 事实基线:2026-09-05 对 `Agentic智能问数在客户营销场景的应用数据集/enterprise.db` 只读摸底所得,以实际库为准。

---

## 1. 目标与设计原则

**目标**:把"表描述.sql + 库内真实数据"整理成 AI 友好元数据,使 `QueryAgent` 在有限 token 内准确理解表结构、编码字典、指标口径与已知陷阱,最终显著减少凭空生成表/字段/指标/结果。

**原则**:
1. **实际库为唯一事实源**。表结构以 `PRAGMA table_info` 为准;取值域、日期范围、编码字典以库内真实数据为准;`表描述.sql` 仅作为业务含义的参考输入。二者冲突时以库为准并记录差异。
2. **结构归引擎、语义走注入**。引擎 `build_schema()` 已自动把 DDL + 每表 2 行样例喂给 LLM;业务语义通过 `QueryAgent(db_path, api_key, biz_context=..., sensitive_columns=...)` 注入(受限列名也走注入,引擎不硬编码)。元数据文件只负责生成高质量 `biz_context`,不进入 `text2sql.py`(铁律 2)。
3. **可机读 + 可人工复核**。机器可读采用 UTF-8 JSON(含中文),人工阅读版为 Markdown。JSON 用于评测 runner / UI / 报告;Markdown 用于队伍评审与数据说明文档复用。
4. **最小必要信息**。只放 LLM 判断口径所需的信息,不放它不需要的(避免 token 浪费与干扰)。每个元数据文件都注明"生成时间、库文件指纹(行数/日期范围)"以便溯源。

## 2. 五类字典设计

元数据由五类字典组成:**表字典、字段字典、指标字典、维度字典、口径字典**。

### 2.1 表字典(table)
一行 = 一张表。字段:

| 字段 | 说明 | 示例 |
|---|---|---|
| `table` | 表名(与库一致) | `dws_cust_aset_d` |
| `layer` | 数仓分层 | `dws`(明细 dwd / 汇总 dws / 应用 ads / 维度 dim) |
| `kind` | 维度表 / 事实表 | `fact` |
| `grain` | 粒度(一行代表什么) | 某客户在某自然日的资产汇总 |
| `pk` | 主键/唯一键(实际库可能无约束,标注"逻辑唯一键") | `data_dt + pty_id` |
| `time_key` | 时间键 | `data_dt` |
| `sys_source` | 是否区分普通/信用账户 | 无(该表天然含 nm+fc 合计口径) |
| `cn_name` | 业务名称 | 客户资产日汇总 |
| `source` | 来源文件 | `dws_cust_aset_d_202606021051.csv` |
| `notes` | 要点/陷阱 | 客户表仅一个快照 20260531,与 Q1 事实错位 |

### 2.2 字段字典(column)
一行 = 一个字段。字段:

| 字段 | 说明 |
|---|---|
| `table` / `column` | 表名 / 列名 |
| `type` | 库内类型(TEXT / REAL) |
| `cn_name` | 中文名 |
| `meaning` | 业务含义(取自 表描述.sql 并校正) |
| `unit` | 单位(元 / 股 / 份 / 笔) |
| `code_dict` | 是否码字段;若是,给 `dim_public.code_type_id` |
| `value_domain` | 库内真实取值域(前 N 高频值 + 是否枚举封闭) |
| `masked` | 是否脱敏 |
| `monetary` | 是否金额(参与汇总口径) |
| `notes` | 特别说明 |

**已确认的码字段清单**(客户表):

| 列 | code_type_id | 库内取值示例 |
|---|---|---|
| `cust_lvl_cd` | 100 | 1000001=紫金理财钻石卡客户 … 1000004=紫金理财银卡客户 |
| `cust_status` | 200 | 2000001=正常、2000004、2000005 |
| `cust_type` | — | 全 'P'(个人),无需解码 |
| `gender_cd` | 500 | 5000002=男(318)、5000003=女(182) |
| `edu_cd` | 600 | 6000003=硕士、6000004=学士、6000005、6000007… |
| `prof_cd` | 700 | 7000032、7000031、7000002=个体工商户… |
| `ccy` | — | 0=人民币、1=美元、2=港币(注意不是 dim_public,是固定口径) |
| `sys_source` | — | nm=普通、fc=信用 |

### 2.3 指标字典(metric)
一行 = 一个指标口径。字段:

| 字段 | 说明 |
|---|---|
| `metric` | 指标名(LLM 识别用户意图用) |
| `aliases` | 同义词(总资产/资产/市值/规模) |
| `formula` | 精确公式(标准 SQL 片段) |
| `unit` | 单位 |
| `tables` | 依赖表 |
| `time_rule` | 时间口径(自然日 / 交易日 / 期末快照) |
| `account_rule` | 账户口径(只 nm / nm+fc / 分账户) |
| `notes` | 陷阱 |

**首批指标口径(库内验证)**,详见 §4 口径字典。

### 2.4 维度字典(dimension)
一行 = 一个可分组维度。字段:

| 字段 | 说明 |
|---|---|
| `dimension` | 维度名 |
| `source` | 直取列 or `dim_public` join or `dim_product` join |
| `join_clause` | 解码 join 模板 |
| `levels` | 层级(如 分公司→营业部) |
| `notes` | 如:`dim_product.prdt_type_name`(二级)、`up_prdt_type_name`(一级);同一一级 ID 存在多名(脏数据,按 ID 归类为准) |

### 2.5 口径字典(caliber)
一行 = 一条"默认口径/易混口径"。字段:`caliber` 名、`default` 默认值、`scope` 适用范围、`evidence` 依据(库内验证结果或 Q&A 共识)、`notes`。这是防"口径幻觉"的关键,M3 的口径校验直接消费它。

## 3. 结构化文件格式(机器可读)

建议目录:`benchmark/metadata/`(与评测同域,runner 直接加载;人工版同步进 `docs/`)。

```
benchmark/metadata/
  tables.json      # 表字典
  columns.json     # 字段字典
  metrics.json     # 指标字典
  dimensions.json  # 维度字典
  calibers.json    # 口径字典
  meta_snapshot.md # 人工可读快照 + 生成时间/库指纹
```

顶层统一信封:

```json
{
  "meta": {
    "generated_at": "2026-09-05T00:00:00+08:00",
    "db": "Agentic智能问数在客户营销场景的应用数据集/enterprise.db",
    "db_fingerprint": {
      "tables": 8,
      "ads_cust_info_d_rows": 500,
      "dwd_cust_hold_d_rows": 408150,
      "dwd_cust_tran_d_rows": 39060,
      "dws_cust_aset_d_rows": 43684,
      "dws_cust_fin_d_rows": 4892,
      "hold_dt_min": "20260101", "hold_dt_max": "20260331",
      "cust_dt": "20260531"
    }
  },
  "items": []
}
```

- `tables.json` 的 `items` = 表字典条目;`columns.json` = 字段字典条目;其余同理。
- 生成方式(M2):纯标准库 Python 只读脚本 `benchmark/build_metadata.py`,从库内 `PRAGMA` + 聚合查询自动抽取值域/日期范围,再合并人工维护的指标/维度/口径定义(JSON 手写),输出上述文件。**M1 只定义格式,不实现脚本。**
  - 注意:`表描述.sql` 为 **GBK 编码(非 UTF-8)**,build_metadata.py 读取时按 `gbk`/`gb18030` 解码;字段含义以库为准原则不变。

## 4. 摸底已确认的业务事实(将进入各字典)

以下事实来自 2026-09-05 只读探查,写文档时作为已确认基线,不再凭空猜测:

1. **8 表**:`dim_branch`(312)/`dim_public`(155)/`dim_product`(334,694)/`ads_cust_info_d`(500)/`dwd_cust_hold_d`(408,150)/`dwd_cust_tran_d`(39,060)/`dws_cust_aset_d`(43,684)/`dws_cust_fin_d`(4,892)。
2. **日期口径(易混,必须进口径字典)**:
   - 客户主档 `ads_cust_info_d` 只有 **20260531** 一个快照;
   - `dwd_cust_hold_d`、`dws_cust_aset_d`:`20260101~20260331` 共 **90 天**(自然日);
   - `dwd_cust_tran_d`、`dws_cust_fin_d`:`20260105~20260331` 共 **56 天**(交易日,1/1–1/4 无数据)。
   - 含义:2026-Q1 = 20260101~20260331;日均 = 区间合计 / 天数(资产类 /90,交易资金类建议 /56 或按题意)。
3. **账户/币种口径**:`sys_source` 仅 `nm`(普通)/`fc`(信用);`ccy` 0=人民币、1=美元、2=港币。资产表 `dws_cust_aset_d` 天然是 nm+fc 并列字段(无 sys_source 列)。
4. **编码字典 `dim_public` 全集**(code_type_id):100 客户等级(钻石/白金/金/银卡…6 值)、200 账户状态(11)、300 证件类型(58)、400 风险等级(保守/谨慎/…/未知,7)、500 性别(未知/男/女/其他,5)、600 学历(硕士/学士/中专/其他,9)、700 职业(59)。**客户表实际只用到子集**(gender 只有男/女;edu 7 值;prof 12 值)。300 证件类型、400 风险等级**有词典、无任何表引用**;业务问"风险等级分布"按**不可答**处理(拒绝并说明),如需映射到客户等级由队伍另行确认。
5. **`dim_product` 分类**:一级 `up_prdt_type_id`(PT02 权证/PT03 债券/PT04 股票/PT05 开放式基金/PT06 衍生品/PT07 理财/PT08 回购/PT09 恒生多金融/PT10 私募/PT11 贵金属/PT99 现金类),二级 `prdt_type_id` 共 57 类(如 沪港通、认估权证、质押代码)。
   - **脏数据点(一级分类名多义)**:`up_prdt_type_id='PT090000'` 的一级分类名同时出现"恒生多金融产品"与"OTC产品";`up_prdt_type_id='PT070000'` 的一级分类名同时出现"理财产品"与"债券"。注意是**一级分类 ID(up_prdt_type_id)名多义**,不是产品 ID(prdt_id 形如 9900265055,按 prdt_id 查不到 PT 码)。字典与 build_metadata.py 一律按 `up_prdt_type_id` 归类,name 仅作展示,防 LLM 被同名误导。
6. **`dim_branch`**:312 营业部(`org_id`)→ 27 分公司(`up_org_id`);营业部名称含 `****` 脱敏(如 `包头******营业部`)。
7. **脱敏**:`ads_cust_info_d.name` 已脱敏(如 `某**`);`sor_pty_id`(经纪客户号)属于疑似个人关联标识,演示/报告中不出现。
8. **买卖字段口径**:`dwd_cust_tran_d` 每行 = 客户×产品×来源×币种×日期;`buy_cnt`(次数)/`buy_mnt`(数量)/`buy_rake`(佣金)/`buy_amt`(金额)/`buy_fare`(费用),卖出同构。**"交易量"未注单位时,本方案默认按金额 `buy_amt+sell_amt` 口径**(此前对拍发现 LLM 会误用股数 `cnt`,必须写进口径字典)。
9. **盈亏口径**(口径字典收录):`盈亏 = (期末总资产 - 期初总资产) + (资金流出合计 - 资金流入合计)`,其中资产用 `nm_tot_aset + fc_pur_aset`,资金流用 `dws_cust_fin_d` 的 `cash/tran/assign` 的 `in/out` 各三列合计。该口径为**队伍口径约定(2026-09-05 对拍结论)**;Q&A.xlsx 已核实为空壳,不作为口径依据。

## 5. 元数据如何注入引擎(不改 text2sql.py)

引擎现状(已核实):
- `QueryAgent.__init__(db_path, api_key, verbose=True, biz_context=None)`:不传时用默认银行库 `BUSINESS_DESC`;显式传入即覆盖(铁律 2 允许的接入口)。
- `_ctx()` 把 `数据库结构 + build_schema(db_path) + 业务说明 + biz_context` 拼成统一上下文,供理解/检索/计划/生成 SQL/解释各阶段 LLM 调用。
- 因此:**表结构由引擎自动取,业务语义由元数据文件生成**,两者天然分离。

注入方式(标准范式,README Appendix 已有):

```python
# 隔离 runner 内(非 text2sql_demo 目录,不入库)
import sys, pathlib
sys.path.insert(0, r"text2sql_demo")
from text2sql import QueryAgent, load_api_key

biz = build_biz_context(metadata_dir="benchmark/metadata")  # M2 实现:读五类字典拼成文本
agent = QueryAgent(
    db_path=r"Agentic智能问数在客户营销场景的应用数据集/enterprise.db",
    api_key=load_api_key(),
    biz_context=biz,   # 企业口径语义经此注入
    sensitive_columns=["sor_pty_id"],  # 受限字段: 样例不外发 + SQL 引用拦截 + 结果列掩码
)
ans = agent.run("Q1 钻石卡男性 40 岁以上客户比亚迪持仓盈亏", clarify=False)
```

`biz_context` 文本模板(由五类字典渲染,控制在 ~1.5–2.5k token):

```
【业务背景】券商客户营销库(2026-Q1 事实 + 20260531 客户快照)。
【表与粒度】<表字典: 每表一行, 粒度/时间键/主键>
【编码解码】dim_public 七类码 + 客户表码字段对照;ccy 0/1/2;sys_source nm/fc。
【产品分类】dim_product 一级/二级;同名脏点: PT090000/PT070000 按 ID 归类为准。
【关键口径】时间(客户快照 20260531;资产/持仓 90 天;交易/资金 56 天);账户(nm/fc);
  总资产 = nm_tot_aset + fc_pur_aset;交易量默认金额口径;盈亏公式(§4.9)。
【易错提醒】客户表无 data_dt 序列(仅一快照);营业部/姓名脱敏;分组多值列按题意取舍。
```

CLI 复用(已有,不改):`python text2sql.py --db <enterprise.db> "问题"` 用默认语义;企业语义必须走上述 runner 注入,不写进引擎(铁律 2)。
